`CLAUDE.md` は作業ツリー・親ディレクトリとも存在しなかった。

## 各段階

1. **解析 score**：任意深さの Linear/SiLU MLP を逆向きの連鎖律で微分する通常の forward 演算を追加。
   initial の `-x`、recursive の observation 項と transition の責任度付き和、mixed の行別選択を維持。
   責任度には参照実装の logsumexp backward と同じ `exp(u-logsumexp(u))` を使い、detach しない。
   anchor/proposal は既存の初期化位置に残し、学習 schedule、score/particle/scale clamp も維持。
   SMI entropy は draw と全混合成分の両依存を含む解析式へ置換。SVGD bandwidth は従来どおり detach。
   固定長 gather による対角除外は従来の行優先順と median を保つ。
   direct/direct_joint の score ネットワークは変更せず、SMI entropy と compile に対応。
   analytic を KAN に指定すると明確なエラー。既定の autograd は引き続き KAN を扱う。
2. **compile**：`_transport_chain` に L 段の transport と必要な最終 score をまとめ、
   `torch.compile(fullgraph=True, dynamic=False)` を使用。branch 判定、`.item()`、入力検証、
   temporal detach、anchor/proposal、schedule 計算、prefix/reset/checkpoint は外側。
   固定ループは trace 時に展開する。branch、shape/stride、dtype/device、入力の勾配状態、
   need_scores、step schedule、train/autocast 状態ごとの callable を再利用し、作成を一度ログ出力する。
   Dynamo のカウンターと backend 呼出回数で二回目に再コンパイルしないことを検査した。
   初回 AOT tracing は private saved-tensor hook 内で一度準備し、その後の実行を外側 checkpoint に戻す。
   これは PyTorch 2.3.1 で tracing のテンソルを checkpoint が捕捉して再入する問題への対処。
   Inductor 自身の CUDA Graphs は無効にし、128 forward の保存領域を暗黙に再利用させない。
   CPU の `InvalidCxxCompiler` のみ警告して eager に戻す。他のコンパイル失敗は隠さない。
3. **CUDA Graphs**：`cuda_graphs.py` に forward/VJP の capture を実装。
   各 autograd node は時刻固有の入力とパラメータの version を保存し、出力を clone する。
   backward 直前にその時刻の入力を静的領域へ戻して forward を再実行し、直後に captured VJP を実行。
   返す勾配も clone するので、後続の replay が蓄積待ちの勾配を上書きしない。
   保持量は各時刻の入力・出力＋signature ごとの workspace。余分な forward と引き換えに、
   全時刻の中間活性を保存せず一括 backward できる設計。capture の warmup は外側 checkpoint の hook から隔離した。
   CPU は一度警告して通常経路を使う。CUDA では analytic が必要。高階の外側微分は非対応。
   [PyTorch 2.3.1 の capture 実装](https://raw.githubusercontent.com/pytorch/pytorch/v2.3.1/torch/cuda/graphs.py)
   とローカルの同版ソースを確認した。**CUDA capture 自体はこの CPU 専用機では未実行**。
4. **検証・計測**：以下の一致テスト、全体 suite、CPU campaign benchmark を実施。

| config key | 既定値 | 選択肢 |
|---|---|---|
| `model.score_implementation` | `autograd` | `autograd`, `analytic` |
| `model.belief_compile` | `off` | `off`, `inductor`（analytic 必須） |
| `model.belief_cuda_graphs` | `false` | boolean（CUDA 上は analytic 必須） |

3キーとも legacy defaults と `EXECUTION_ONLY_KEYS` に登録。
古い resolved config の正規化・再開時比較に対応し、重みや optimizer の形式は変更しない。

## 残るリスク

- **GPU 未検証**：capture の可否、Inductor の数値差、AOT backward と manual capture の併用、
  checkpoint hook の相互作用、128時刻の peak memory と速度はサーバーで確認が必要。
  GPU テストが通るまで有効化を本番検証済みとは扱わない。失敗を eager に黙って隠す実装にはしていない。
- signature ごとに private workspace を持つため、prefix の多数の batch shape は compile/capture 初期費用とメモリを増やす。
  benchmark の時間には初回費用が入る。長い実運用では初回と定常更新を分けて計測すること。
- 同じ数学でも bitwise 同一ではない。診断用 lr=0.001 の初回 Adam では SVGD の attention key bias が
  **1.13e-4** 異なり、SMI の transition 最終 bias にも許容差超過があった。
  どちらも理論上不変な方向の約1e-9以下の勾配差が Adam に増幅されたもの。
  campaign の lr=0.00025 は基準内だが、異なる学習率・長期学習の一致まで保証しない。
- capture は同じ CUDA stream で再利用し、optimizer 更新は系列の backward 完了後に行う。
  forward と backward の間で parameter を変更した場合は通常の autograd version check が拒否する。
  外側の高階微分や並行した複数 stream の workspace 共有は対象外。

## GPU validation round 2

The first server run failed during backward capture; CUDA has not been available
for this repair. The old code already used the same explicit stream for forward
and backward, so merely changing that stream argument is not a sufficient fix.
Autograd records streams on nodes (including leaf AccumulateGrad), not just on
tensor storage. A retained warmup graph or parameter node from eager work can
therefore make backward synchronize outside the capture stream. The old warmup
retained its last outputs; PyTorch's helper explicitly deletes its warmup outputs
and input gradients. The trace alone does not identify the particular offending
leaf, so the GPU tests below must confirm the diagnosis.

Training capture now uses torch.cuda.make_graphed_callables on a module wrapper:
three side-stream forward/backward warmups, synchronization before capture,
matching default capture contexts and one shared forward/backward pool are all
owned by the installed torch 2.3.1 implementation. Capture parameter leaves are
detached aliases of the real parameters, substituted with torch.func.functional_call.
They share current weight storage but cannot reuse eager AccumulateGrad nodes.
The outer node still saves the original parameters for version checks and returns
their gradients. Before every deferred backward it reruns the graphed forward,
then immediately consumes that library autograd node; outputs and returned
gradients are cloned. Inference retains a separate forward-only capture because
the 2.3.1 library helper unconditionally invokes autograd.grad. It also performs
three side-stream warmups and synchronization.

Capture errors are chained into a clear restart-required error, and an outer
device/stream context restores the caller even if graph.__exit__ fails. Failed
runners never enter the belief cache. **This is the brief's explicit-error
fallback, not guaranteed in-process RNG recovery.** In torch 2.3.1,
cudaStreamEndCapture can throw before allocator cleanup and capture_epilogue;
reset() or restoring the RNG byte state does not repair those private flags.
Stop at the first GPU test failure and restart Python before further CUDA work.
See the pinned [autograd stream semantics implementation](https://raw.githubusercontent.com/pytorch/pytorch/v2.3.1/torch/csrc/autograd/engine.cpp)
and [CUDAGraph cleanup implementation](https://raw.githubusercontent.com/pytorch/pytorch/v2.3.1/aten/src/ATen/cuda/CUDAGraph.cpp).

CPU tests now cover independent autograd leaves with shared storage, eager and
precompiled bound callables, weight updates, 2/16/128 deferred steps including
unused parameters, parameter version checks, wrong-stream rejection, failure
chaining/stream restoration, and inference warmup/placement decisions. These
mock stream control only, not CUDA behavior. The GPU suite is retained and now
also tests live eager parameter nodes on default/side caller streams and inference.

TRITON_LIBCUDA_PATH must name the host NVIDIA driver directory containing
libcuda.so (not a CUDA toolkit stub directory). The example below uses the

elsewhere. Run each command from the repository root in a fresh shell/process

## GPU validation round 3

The supplied server result was 34/38 CUDA-graph-file tests passing. Three failures
involved compiled capture losing gradients to private parameter leaves; the fourth
was float32 gradient roundoff across 128 steps. This repair uses the brief's
explicit-error fallback for the combination, rather than claiming compiled capture
is exact. An attempted explicit-parameter functional wrapper failed the local
PyTorch 2.3.1 `aot_eager`, `fullgraph=True` check at `torch.func.functional_call`
(`Unsupported: ... NNModuleVariable() ConstDictVariable() TupleVariable()`). That
attempt is not retained, and no Dynamo internals are patched to bypass the failure.

`belief_compile=inductor` together with `belief_cuda_graphs=true` now raises a
clear `ConfigError` during config validation and direct `EnergyBelief` construction.
The same check runs before replay work, so changing flags after construction cannot
bypass it, even on CPU. The message explains the gradient issue and the two valid
choices: compile off with graphs, or Inductor with graphs off. `_CaptureModule`
also rejects directly supplied Dynamo-compiled functions/modules. CPU regression
tests warm actual `aot_eager` callables before checking rejection; the eager alias
test still checks independent leaves, shared/live storage, parameter restoration,
and gradient ownership. The two combined GPU cases are replaced by CPU rejection
coverage; graph-only optional-score and sequence tests remain, as do standalone
Inductor tests.

Only `test_cuda_graph_128_steps` now supplies gradient `atol=1e-4`; `rtol=1e-5`
is unchanged. The measured server discrepancy was 8.65e-5 absolute / 2.82e-5
relative for one of 104 elements. Capture may select different cuBLAS kernels,
and float32 rounding accumulates across the long recurrence. As with the Adam
roundoff discussion in `test_speedup_exactness.py`, the absolute allowance is
specific to the observed amplification. All 2/16-step gradient checks remain at
`atol=rtol=1e-5`, outputs remain at `1e-6`, and None/tensor gradient matching is
still required. The new 128-step tolerance has not been exercised on a GPU here.

Benchmark investigation found no Inductor-specific one-update limit. The old
`ppo.total_steps=128` with 4 environments and 16 steps schedules only two PPO
updates, plus one extra prediction pretrain update. The trainer calls the timing
phase `ppo_update` for prediction too: update 1 is pretraining, not policy PPO.
Also, the parent previously hid all child output until the child terminated.
The supplied excerpts contain no CUDA benchmark exit code or complete log, so
they cannot establish whether that server process crashed, was killed, or was
still compiling after its first timed update.

The benchmark now runs one prediction pretrain update, one PPO warm-up, then
**three measured PPO updates** by default (`ppo.total_steps=256`). Flags permit
more warm-up/measured updates, with minimums of 1 and 3. Interleaved prediction
phases are disabled for this small campaign. The `graphs` setting uses analytic
scores with compile off, and does not probe Inductor. Children run unbuffered;
the parent streams and flushes logs as they arrive. Nonzero exits, killed children,
missing/incomplete phase records, and incomplete checkpoints produce a named
`ERROR`, a log path, and an error entry in `timings.json`. Remaining settings still
run in fresh processes; the parent exits nonzero if any setting failed. A zero
exit after one update is explicitly rejected. Results are saved after each setting.
Regression tests cover exits 1/-9 and zero-exit truncation, plus separation of
pretraining, PPO warm-up, and measured timings.
